# 数据模型变更台账

橡果的数据格式每动一次，就在这里追加一节。**这是唯一的字段变更记录**——
`src/core/model.ts` 的注释只留一句摘要，README 的架构表指向这里。

为什么要有它：迁移逻辑写在 `migrate()` 里，但「这个字段是什么时候加的、老数据里是什么、
缺了补什么」这些事代码本身讲不清楚。没有台账，下一次改模型只能靠考古。

## 怎么写一节

每节固定六栏，缺一栏都别提交：

1. **版本区间与日期** —— `v5 → v6` 或 `v5 内附加`，配上 app 版本和日期
2. **字段差异表** —— 新增 / 改名 / 语义变更 / 删除，每行写：路径 · 类型 · 老数据里是什么 · 新数据里是什么
3. **转化规则** —— 缺失补什么默认值（写清是 `null` 还是 `undefined` 还是推导值）、被删字段怎么丢、被改字段怎么换算
4. **要不要升 DATA_VERSION** —— 判据 + 本次结论
5. **联动清单** —— 哪些文件跟着改（漏改联动处是这个项目最常犯的错）
6. **测试清单** —— 本次新加了哪几条用例，在哪个文件

### 升不升 DATA_VERSION 的判据

> **老客户端把这份数据读进来、再存回去，会不会丢东西或写坏？**
> **它还会不会继续写入新客户端读不明白的数据？**
> 任一条为「会」→ 必须升。只是它看不见新字段、但 spread 能原样带走，
> 而且它写出来的东西新客户端也认 → 不升。

第二问是 2026-08-31 补上的（v5 → v6 那次），此前漏了。只查「读进来再存回去」是不完整的：
老客户端不是一个只读的旁观者，它一直在往同一本账里写。子任务的 `doneAt` 就栽在这里——
老客户端 spread 确实不丢已有的戳，但它自己勾掉的子任务**永远不带戳**，
新客户端拿到只能猜是哪天做完的。**只查读、不查写，判据就是漏的。**

不是「凡改模型必升」。升版本是有代价的，而且**不可回退**：任一台新客户端推一次，
服务端 `vaults.schema` 就被 `MAX(旧, 新)` 锁到新版本（`server/app/db.py`），
所有老设备当场停止同步（`cloud.unpackRemote` 抛 `client_too_old` →
`syncCtl` 置 `needsUpgrade`，pull 和 push 一起停），只有发一版新客户端才能解开。

判据里唯一的例外要盯住：`migrate()` 里**墓碑是显式重建的**
（`graveyard.map(g => ({ id: g.id, at: g.at }))`），是全代码唯一会丢未知字段的地方。
给 `Tombstone` 加字段 → 老客户端过一遍就把它抹了 → **必须升版本**。
其余结构都靠 spread 天然保留未知字段。

## v5 → v6 · 子任务的完成时刻 + 「放弃」（2026-08-31 / 09-01，v1.9.0）

> **一次升版本，两处改动**。`doneAt` 与 `droppedAt` 都落在 v6 里，
> **不再为「放弃」单独升一次**：v1.9.0 还没发布，schema 6 一次到位，
> 少一次把手机端踢出同步的动作（那个代价见下面「要不要升 DATA_VERSION」）。

### 字段差异表

| 变更 | 路径 | 类型 | 老数据里是什么 | 新数据里是什么 |
| --- | --- | --- | --- | --- |
| 新增 | `Task.subtasks[].doneAt` | `string \| null`（可选） | 没有这个键 | ISO 完成时刻；没勾上或来历不明的是 `null` |
| 新增 | `Task.droppedAt` | `string \| null`（必填） | 没有这个键 | ISO 放弃时刻；没放弃的是 `null` |
| 新增 | `Task.subtasks[].droppedAt` | `string \| null`（可选） | 没有这个键 | 同上，管的是「这一步不做了」 |

「放弃」是什么：完成之外的**第二种收场**——这件事不做了，但它没做成。
圈圈只管完成（一点都没动），放弃体现在标题旁边一个灰色小标签「已放弃」上。

### 转化规则

- **缺失补 `null`，不补 `undefined`**：`undefined` 会被 `JSON.stringify` 整个吞掉，
  「导出 → 导入 → 再导出逐字节一致」当场就不成立了（`tests/transfer.test.ts`）
- **已经勾掉但没有完成时刻的老子任务，补的还是 `null`**，绝不拿「现在」冒充。
  两个原因：一是那本来就不知道是哪天做完的，编一个时刻是撒谎；
  二是 `stampChanged`（`store.ts`）用 `JSON.stringify` 比内容判「这条动没动过」，
  在迁移层给全库补戳 = 全库 `updatedAt` 刷新 = 下一次同步拿本机盖掉云端
- **兜底放在渲染层**：读的时候走 `store.rowDoneAt`，
  `sub.doneAt ?? task.doneAt ?? task.createdAt`——老子任务跟着母任务的完成日走，
  不单开「不知道哪天」那一组（那种组只会越攒越大，还谁也修不了它）
- **回落到 `createdAt` 那一档只用来排序，不算完成记录**：判据是
  `store.rowDoneGuessed`（`sub && !sub.doneAt && !task.doneAt`）。
  这类行**一条都不进日历**（否则用户会在什么都没做完的那天看见一条 ✓，
  日格的绿点数字也跟着虚高）；「已完成」视图仍然列出来，但沉到最后一组的尾部，
  且 `doneDate` 传 `null`，不写「完成 X 月 X 日」。宁可不说，也不编一个日期
- **循环任务推进到下一轮时 `doneAt` 清成 `null`**，跟 `done` / 子任务自带日期同口径：
  它记的是上一轮的完成时刻。上一轮的记录留在已完成副本里，那份**保留** `doneAt`

`droppedAt` 的转化规则：

- **缺失一律补 `null`**，任务级和子任务级都是（理由同 `doneAt`：`undefined` 会被
  `JSON.stringify` 吞掉，「导出 → 导入 → 再导出逐字节一致」当场不成立）
- **没有「猜的」那一档**：`droppedAt` 是这一版才有的字段，老数据里不存在任何一条已放弃的记录，
  凡是带标记的都必定带着时刻。所以不需要 `rowDoneGuessed` 那种兜底，
  `rowDroppedAt` 里那个 `?? task.createdAt` 只是类型上的保底，实际取不到
- **跟 `done` / `doneAt` 互斥**，两个方向都要清：勾完成 → `droppedAt = null`；
  标记放弃 → `done = false, doneAt = null`。任务级落在 `completeTask` / `completeTasks` /
  `dropTasks`，子任务级**统一落在 `applySubPatch`**（勾子任务有三条独立的路，
  在调用点各写一遍必漏，跟 `doneAt` 栽过的坑是同一个）
- **循环任务放弃 = 这一轮不做了，照样推进到下一轮**（跟完成同一套推进逻辑）：
  留一条 `droppedAt` 非空的副本作历史，本体推到下一个落点，
  **推进后的新一轮 `droppedAt` 必须清成 `null`**，子任务的那份一并清——
  否则新一轮一出生就被判死刑。要彻底不做请用删除，那是另一个键
- **统计里单独算一档**：既不算完成也不算未完成。`byList` / `byWho` 的 `open` 栏把它剔掉，
  `weeklyReview` 新开一个 `dropped` 数组，`completionByDay`（热力图/趋势）只数完成，
  一件都不许并进去——并进去完成率就虚高，那个数字整页作废

### 要不要升 DATA_VERSION

**升，5 → 6。**（2026-08-31 用户当场拍板，推翻了本节最初写的「不升」）

判据两问过一遍：

- **老客户端读进来再存回去会不会丢？** 不会。`migrate` 的子任务分支是 `{ ...默认值, ...s }`，
  spread 把不认识的 `doneAt` 原样带过去；子任务不是墓碑那种被显式重建的结构。
- **老客户端会不会继续写入新客户端读不明白的数据？** **会，而且是天天写。**
  手机上那台老客户端勾子任务走的是它自己的 `updateSubtask`，只置 `done: true`，
  压根不会盖 `doneAt`。用户今天在手机上勾一条，同步到桌面就是一条没有完成时刻的已完成子任务，
  桌面只能猜——按上面的判据落进「猜的」那一档，不进日历、不写日期。
  用户的感受是「我手机上刚勾的，电脑上今天找不着」。这不是理论情况，是上线即发生的日常路径。

最初那版结论只答了第一问就写了「不升」，漏的正是第二问。**判据本身也一起补全了**（见开头）。

`droppedAt` 两问过一遍，结论是**并进这一次**（不另开 v7）：

- **读进来再存回去会不会丢？** 不会，`Task` 和 `Subtask` 都靠 spread 原样带走未知字段。
- **老客户端会不会继续写入新客户端读不明白的数据？** 会。老客户端整个不认「放弃」这回事：
  一件在新客户端上标了放弃的事，在它那儿照旧躺在待办里，它顺手改一下、勾一下都会写回来。
  按判据这也该升。
- 但 v6 **还没发布**，schema 6 里一次装下 `doneAt` 和 `droppedAt` 就够了。
  为它单独再升一次 = 白白多一次把手机端踢出同步的动作，纯亏。

代价与用户裁定：升到 6 会立刻把手机端踢出同步（服务端 `vaults.schema` 一被顶到 6，
手机上那台 v1.7/v1.8 就 `client_too_old`，pull 和 push 一起停）。用户裁定这个代价可以接受，
原话是「目前云服务器既然没有收到手机的数据，那就是没有同步，那就直接云端数据下载下来覆盖就好了」——
**云端从未收到过手机端的数据，手机那边没有值得保的东西**，等手机端追平时从云端拉一份覆盖本地即可。

**不可逆，记牢**：服务端 `vaults.schema` 是 `MAX(旧, 新)` 单调只升不降（`server/app/db.py`），
桌面端一旦推上 6 就**回不去了**——降级装回 v1.8.0 也解不开，那台反过来会被判 `client_too_old`。

### 联动清单

Subtask **没有工厂函数**（Task 有 `newTask()`），默认值分散在两个手写字面量里，
加字段必须两处都改，漏一处就出脏数据：

- `src/core/model.ts` —— `Subtask` 接口；`migrate()` 里子任务那个字面量补 `doneAt: null`
- `src/core/store.ts` —— `addSubtask` 的构造补 `doneAt: null`
- `src/core/store.ts` —— 新增 `applySubPatch()`：**勾/取消的盖戳与清戳统一落在这一层**。
  勾一条子任务有三条独立的路（任务卡走 `toggleSubtask`，`TaskRow` 和 `ContextMenu`
  直调 `updateSubtask({done})`），在三个调用点各写一遍迟早漏一处，
  漏了就是「在卡上勾有完成日、在行上勾没有」的分裂数据
- `src/core/store.ts` —— 循环推进的**两处**（`completeTask` 单条、`completeTasks` 批量，
  是复制粘贴的双胞胎）补 `doneAt: null`；两处的已完成副本 `{...s, id: newId()}` 保留 `doneAt` 不动
- `src/core/store.ts` —— 新增纯函数 `doneRows()` / `rowDoneAt()` / `rowDoneDay()` / `rowDoneGuessed()`
- `src/views/Done.tsx`、`src/views/Calendar.tsx` —— 读取方，共用上面那几个函数

`droppedAt` 的联动清单（构造 / 复制 / 迁移点一个不许漏，**跟上面那批逐条对应**）：

- `src/core/model.ts` —— `Task.droppedAt`（必填）与 `Subtask.droppedAt`（可选）两个接口字段；
  `newTask()` 补 `droppedAt: null`；`migrate()` 里子任务那个手写字面量补 `droppedAt: null`
  （任务级靠 `{ ...newTask(...), ...t }` 自动带上）
- `src/core/store.ts` —— `addSubtask` 的构造补 `droppedAt: null`
- `src/core/store.ts` —— `applySubPatch()` 里加互斥两条（勾完成清放弃 / 标记放弃清完成）
- `src/core/store.ts` —— `completeTask`、`completeTasks`、**新增的 `dropTasks`** 三处循环推进
  （原来是双胞胎，现在是三胞胎，改一处必须回头看另两处）：
  已完成/已放弃副本、`advanced` 本体、`advanced.subtasks` 三层都要处理 `droppedAt`
- `src/core/store.ts` —— `setTaskKind` 转成习惯时清 `droppedAt`（习惯没有放弃这回事）
- `src/core/store.ts` —— `openRows()` 跳过已放弃的任务和已放弃的子任务
- `src/core/store.ts` —— 新增 `dropTasks()` / `dropSubtask()` / `droppedRows()` /
  `rowDropped()` / `rowDroppedAt()` / `rowDroppedDay()`
- `src/core/stats.ts` —— 新增 `isDropped()` / `isDroppedInRange()`；
  `byList` / `byWho` 的 `open` 剔除；`weeklyReview` 新增 `dropped` 并从
  `stillOpen` / `postponed` 里剔除；`exportWeekMarkdown` 加「本周放弃」一节
- `src/views/Quadrant.tsx`、`src/views/Calendar.tsx` —— 待办侧各加一条 `!t.droppedAt`
  （今天 / 计划 / 侧栏那两个计数走 `openRows`，自动跟随，不用各改一遍）
- `src/core/reminders.ts` —— `sweep()` 的到点名单加 `!t.droppedAt`：都说了不做了还弹一下是纯打扰。
  **提醒字段本身不清**，取消放弃之后它原样回来
- `src/views/ListView.tsx`（随手记 / 清单 / 需求方 / 标签）四个 filter 各加一条 `!t.droppedAt`；
  `store.allWho` / `allTags` 与 `Sidebar` 的 `open` 计数同步剔除；`views/FocusView.tsx`
  的随手记候选一并跟上。
  **口径（v1.9.0 收口时定的，先前那版是两套）**：放弃跟已完成**一模一样**——已完成在这四个
  视图里是「整条隐藏 + 不进计数」，放弃就照抄这一条，不发明第三种行为。
  先前那版让这四个视图收留已放弃的事、侧栏也照算，理由是「看得见上下文、多一个取消放弃的入口」，
  但 `stats.ts` 的 `byList` / `byWho` 已经把放弃剔出 open 栏了——同一个「还欠几件」在
  侧栏、视图、统计页给三个值，用户对不上的时候只能当哪个是坏的。取消放弃的入口在
  「已完成 → 放弃的」里点圆圈，跟取消完成同一个地方，不缺这一个
- `src/views/Done.tsx` —— 顶上三选一「做完的 / 放弃的 / 全部」，默认「做完的」，
  选择存 `localStorage` 的 `acorn-done-filter`（控件与存法照抄日历那个筛子）
- `src/components/TaskRow.tsx` —— 删除线 + 「已放弃」灰标签；
  「N/total」进度把放弃的踢出分母；「已完成」视图里的日期文案分「完成 X」/「放弃 X」
- `src/components/TaskCard.tsx` —— 标题旁的灰标签；chips 那排 `tc-gap` **之后**的放弃键
  （跟 🗑 一档，都是「按下去东西会从列表里消失」的键）；子任务行上的 `sub-drop`
- `src/components/ContextMenu.tsx` —— 任务菜单与子任务菜单各加一项「放弃 / 取消放弃」
- `src/views/Settings.tsx` —— 导出 CSV 的「状态」列变三态（已完成 / 已放弃 / 未完成）
- `src/styles/app.css` —— `.dropped-row` / `.drop-tag` / `.sub-drop` / `.drop-pill`
- **没动的**：`src/core/syntax.ts` 与 `src/core/parse.ts` **一个字都没加**。
  便捷语那套词表动一下就会打断「整句改」的往返（写出来的句子必须能原样解析回同一件事），
  「放弃」这轮不进语法

升版本这一下自己也有联动，四处字面量 + 两处版本号（这次一并改了）：

- `src/core/model.ts` —— `DATA_VERSION`、`AppData.version` 的字面量类型、
  `defaultData()`、`migrate()` 的返回，四处一起改到 6
- `package.json` 与 `src-tauri/tauri.conf.json` —— 版本号一起改成 `1.9.0`。
  **必须同步**：只改一个会让「装完还提示有新版」变成死循环
  （`src-tauri/Cargo.toml` / `Cargo.lock` 也跟着改，保持三处一致）
- `tests/` 里那些 `{version: 2/3/4}` 的老数据 fixture **不跟着改**——
  它们是 `unknown` 入参，扮演的就是老版本导出的文件，改了这批用例就白写了

### 测试清单

- `tests/migration.test.ts`（**新建**，以后每次模型变更的模板）：v1~v5 各一条升级路径、
  `migrate` 幂等、未知字段不丢（含墓碑会丢字段的「锁现状」断言）、
  老子任务补的是 `null` 不是 `undefined`、已勾掉的老子任务也只补 `null`、
  `migrate` 不刷新任何 `updatedAt`、循环推进两处（单条 + 批量）的 `doneAt` 清空与副本保留
- `tests/store.test.ts`：`addSubtask` 自带 `doneAt: null`；`toggleSubtask` 与
  `updateSubtask({done})` 盖戳/清戳一致；不碰 `done` 的补丁不动戳；显式给 `doneAt` 时以调用方为准
- `tests/subtasks.test.ts`：`doneRows` 出行规则、按件去重、完成日三级回落、归日转本地时区、
  `rowDoneGuessed` 四条（有自己的戳 / 跟母任务的戳 / 两边都没戳 = 猜的 / 母任务行不算猜的）
- `tests/schema-guard.test.ts`：本地文件比本机新时 `loadData` 报 `tooNew`、
  `initStore` 停下不落库、内存里那份换成真正的空账本、这个状态下改了东西也存不下去
- `tests/sync-guard.test.ts`（**新建**）：`dataTooNew` / `rescue` / `loadError` 三种状态下
  `syncNow` 一次都不碰云，外加一条「一切正常时确实会推」的对照组

`droppedAt` 这一半的测试都在 `tests/dropped.test.ts`（**新建**，49 条），分七组：

- **构造与迁移**：`newTask` / `addSubtask` 自带 `droppedAt: null`（断言的是
  `"droppedAt" in s`，不是 `?? null`——防的正是 `undefined` 被 `JSON.stringify` 吞掉）；
  v5 老数据升上来两级都补 `null` 且没有一件被误判成放弃；`migrate` 幂等
- **动作**：盖戳 / 幂等（再放弃一次不重复盖、不白压撤销栈）/ 取消放弃回到未完成 /
  进撤销栈且 toast 可撤销 / 批量只压一层 / 习惯不给放弃
- **互斥**：两个方向各一条，子任务那条把三条路都走一遍
- **循环推进**：副本保留上一轮、本体推到下一个周一、新一轮与其子任务的 `droppedAt` 都是 `null`、
  无日期的循环任务就地放弃不推进、完成那条路推进后同样清空
- **去哪**：`openRows` 三种情形（整件事放弃 / 只放弃一步 / 每步都放弃时母任务行回来收尾）、
  `tasksForToday` 三个桶都不收留
- **`droppedRows` 家族**：出行规则、回收站不出、`rowDropped` 按行判、
  归日转本地时区、**`doneRows` 一条放弃的都不收**（日历就是靠它画的）
- **统计**：完成数不含放弃、`stillOpen` / `postponed` 剔除、`byList` / `byWho` 两栏都不加、
  周报「本周放弃」一节的有无、整周只有放弃时不能报「本周没有记录」
- 另有**结构性约束**（读源码钉住，路数同 `tests/wipe.test.ts`）：圈圈那两处逻辑里没有放弃的影子、
  放弃键排在 `tc-gap` 之后而不在胶囊排里、四象限与日历明写了 `!t.droppedAt`、
  「已完成」那个三选一的三个档位与 localStorage 键

### 升版本之后必须做什么

- **手机端追平时必须发一版 schema 6 的 APK**。不发，手机端就一直停在「需要升级」，
  同步永远不恢复。`server/deploy/publish-apk.sh` 会自动从 `model.ts` 抠新 schema，
  不用手填——但也正因为是自动抠的，**发包前务必确认这一版代码里的 `DATA_VERSION` 已经是 6**
- 手机端追平的那一次，按用户裁定**从云端拉一份覆盖本地**即可：
  云端从未收到过手机端的数据，本地那份没有值得保的东西
- 桌面端这边**没有回头路**（服务端 schema 单调只升），所以别拿「大不了降级」当后备方案

## 别忘了的几件事

- `migrate()` **不是版本阶梯**，是一次性「按当前模型补默认 + 归一化」的幂等函数，
  它根本不读 `d.version`。想重构成 `switch (version)` 会把上面所有老数据用例一起推翻，别动它的形状
- 版本号有 **4 处字面量**要一起改：`model.ts` 的 `DATA_VERSION`、`AppData.version`（**字面量类型**，
  漏改会编译报错，这是唯一的编译期兜底）、`defaultData()`、`migrate()` 的返回。`merge.ts` 自动跟随
- `server/deploy/publish-apk.sh` 用 sed 从 `model.ts` 抠 `DATA_VERSION`，正则写死了
  `^export const DATA_VERSION = <数字>;`。改这行的写法（同行加注释、改成 `as const`、
  换成从别处 import）会让脚本抠不出来，或者更糟——抠出旧值发布出去
- 服务端 `MIN_SCHEMA`（`server/app/main.py`）现在是 3，是硬下限：schema < 3 的客户端直接 400。
  调高它等于主动淘汰一批版本，要在这里记一笔
